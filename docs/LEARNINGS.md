# Learnings

This file stores durable engineering lessons for future agents working on PureSOC.
Keep entries short, specific, and actionable.

## Current Learnings

- The repository uses the shared AI project template layout: root files are for discovery and durable docs, while application code lives under `code/`.
- PureSOC path references in implementation prompts are app-relative unless they explicitly start with `docs/` or another root-level path. For example, `apps/api` means `code/apps/api`.
- The default Compose catalog is build oriented: PureSOC app services include `build:` and `pull_policy: build`, then tag local outputs as `puresoc-*:local`; deployment apps must support Compose builds rather than relying on prepublished PureSOC registry images.
- Do not make `code/compose.yml` image-only while keeping `puresoc-*:local` tags; single-file deploy runners will try to pull those local tags from a registry and fail before containers start.
- Avoid Docker Hub for app Dockerfile base images and bundled data-service defaults where practical; some deployment builders fail with anonymous-token fetch errors. Use public ECR Docker Library images for Node/Postgres/Redis and Quay for MinIO. Keep `PURESOC_CLAMAV_IMAGE` overridable because the ClamAV upstream image is Docker Hub-hosted.
- The compliance engine must remain provider-neutral. Microsoft 365 details belong under `code/packages/providers/microsoft365`.
- EU NIS2 baseline logic and Romania country-pack logic must stay separate. Romania-specific code belongs under `code/packages/compliance/nis2/country-packs/ro`.
- Regulatory workbook/source mappings are application data under `code/data/regulatory`; do not hardcode workbook-derived rules in UI code.
- Provider write/remediation actions stay disabled until audit logging, approval, preflight, snapshots, verification, and evidence metadata exist.
- Cross-package TypeScript imports must use `@puresoc/*` package exports; `code/scripts/check-layout.mjs` rejects deep relative package imports, deep package subpaths, and missing workspace dependency declarations.
- Legal-caveat copy is message-keyed and falls back to English for Romanian locale until product/legal approves Romanian wording.
- M58 adds shared message-catalog resolution with requested/resolved locale, fallback reason, message key, and review status. Keep legal Romanian copy absent until approved; use demo-safe Romanian product labels only for non-legal UI copy.
- Romania notification draft labels are country-pack-owned message keys. They currently resolve English/source-mapped labels for Romanian requests with `missing_translation` metadata rather than claiming approved Romanian regulatory copy.
- Future country-pack notification drafts should use the generic `NotificationDraft.payloadJson` envelope with a versioned schema key; Romania-specific draft tables are compatibility/workflow companions, not the default pattern for new countries.
- Generic notification draft writes should validate the payload envelope semantics before persistence, including keyed legal caveat metadata and source-mapped fields.
- Runtime notification draft writes should create the generic `NotificationDraft` first; Romania companion rows only add RO workflow links such as onboarding/classification IDs.
- Stored analysis/report/dashboard runtime data uses the `OutputRecordRepository` boundary; the Prisma adapter stores analysis evidence alongside existing `compliance_result_snapshots.resultSetJson` and must preserve checklist items written by compliance-result persistence.
- Internal-readiness CSV exports are generated from stored analysis report data through `@puresoc/reports`; keep CSV output deterministic, legal-caveated, source-referenced, and organization-scoped, and store generated CSV files as evidence metadata instead of exposing storage URIs.
- Generated JSON/CSV report exports should also create server-side `report_exports` metadata through `OutputRecordRepository` with organization-scoped reads, ready status, format, and content hash. Keep storage URIs out of API responses.
- Generated PDF report exports use the internal `puresoc-report-renderer` Playwright service from `PURESOC_REPORT_RENDERER`; they must be stored as generated-report evidence, record `GeneratedReport.contentHashSha256` and `report_exports` hash metadata, and return through the audited `EvidenceApiService.download` path so `EvidenceAccessLog` captures direct PDF downloads.
- Notification channels, logs, and deadline alert sources are organization-scoped runtime data. Slack/Teams webhook destinations must be stored server-side and rendered only as previews in API/UI responses; tests should use injected transports unless disposable SMTP/webhook credentials are explicitly approved.
- M94 scheduler alert windows are intentionally narrow and local: incident deadlines at roughly six hours out, evidence expiring roughly seven days out, and checklist due dates in the scheduler scan interval. The `notification_deadlines` table is a minimal alert source, not a full incident workflow model.
- M95 dashboard trend metrics are additive to `DashboardSnapshotContract.trendMetrics`: the chart score is compliant plus accepted-risk controls over total controls, not the existing weighted `overallInternalReadiness` score. Daily scheduler de-duplication uses UTC calendar days, and provider connection health counts provider-neutral connections that are `connected` and read-enabled.
- Internal-readiness evidence packages are deterministic local tar bundles built by `@puresoc/reports`; they include a manifest, JSON report, CSV export, and locally readable evidence files, then record a `binary_evidence_package` export row and generated-report evidence artifact without exposing storage URIs.
- Evidence package exports enforce configurable local guardrails for maximum evidence file count, per-file bytes, and total bundle bytes through `PURESOC_REPORT_EVIDENCE_PACKAGE_MAX_*` settings. Oversized packages return stable report-export errors and must not create generated package evidence artifacts or `binary_evidence_package` export rows.
- Identity/session/organization/RBAC runtime data now uses the selected identity repository boundary; backend authorization checks should use `services.rbacRepository`, not the legacy in-memory `services.repository` field.
- Memory-mode API repositories are split by context under `services.memoryRepositories`: identity/org/RBAC, evidence, and billing are separate adapters. Tests should inspect the specific context repository instead of a shared `services.repository` god-object.
- `apps/api/src/server.ts` dispatches through `apiRouteTable` entries with method, pattern, route family, and handler metadata. Stripe webhook raw-body handling remains a `rawBody` route path before JSON parsing; middleware route-family behavior still comes from `resolveRoutePolicy`.
- Audit log runtime data now uses the selected audit sink boundary; Prisma mode persists redacted canonical payloads and hash metadata.
- Partner tenant-access audit metadata should use redaction-safe keys such as `tenantSessionId`, `effectiveOrganizationId`, and `reason`; response and audit guards intentionally treat field-name fragments like `access` and `token` as sensitive.
- Partner-created customer companies should be tenant-only organizations plus `PartnerTenantGrant`, not ordinary organization memberships for the partner actor. Otherwise partner permissions bypass the explicit grant/session model.
- Prisma audit appends use a transaction-scoped PostgreSQL advisory lock keyed by audit scope plus persisted `scopeKey`/`chainSequence` ordering. The chain sequence is the deterministic latest/export order; `createdAt` alone is not enough when concurrent writes share a timestamp.
- In-memory audit writes are serialized only within one Node.js process for deterministic local/tests. Do not treat memory mode as multi-process or persistent audit hardening.
- Audit export/checkpoint data is database-only and tamper-evident, not WORM storage or external notarization. Checkpoints preserve terminal hashes for later anchoring, include retention/export policy metadata, and checkpoint creation audits are appended after the covered segment.
- The audit external checkpoint provider contract currently supports only `none` and deterministic `fake-local`; `fake-local` is test-only local metadata, not a timestamp authority, signer, KMS/HSM, WORM store, or production notarization.
- Audit export handoff metadata is descriptive runbook state. `database_only`, `worm_export_pending`, `externally_anchored`, and `external_anchor_failed` do not change the default non-WORM/non-notarized guarantees; failed anchor metadata must remain generic and secret-free.
- Provider connection/telemetry runtime data now uses the selected `ProviderResourceStore`; Prisma mode persists provider-neutral connection metadata, encrypted credential envelopes, permission bundles, capabilities, sync runs/modules, raw and normalized resources, findings, and recommendations.
- Microsoft 365 is a tenant-owned provider connection in the product UI/API: customer tenant IDs, consent metadata, permission bundles, tokens, module status, and capabilities live under `ProviderConnection`. Any Microsoft connector app registration values are platform connector configuration, not a global customer tenant connection.
- The served Microsoft 365 connector page is `/providers/microsoft365` and must remain usable before Romania onboarding answers or dashboard snapshots exist. New workspaces intentionally land there so a tenant admin can approve the PureSOC platform app first.
- Microsoft 365 admin-consent URL generation uses Microsoft identity platform v2 `/organizations/v2.0/adminconsent` with `scope=https://graph.microsoft.com/.default`. When bundles are omitted, the connector requests the full V1 read-only set: baseline, security, and Intune; write bundles stay rejected.
- Microsoft 365 admin-consent callback state lives in `provider_consent_states` as a single-use hash in Prisma mode; do not reintroduce process-local state as an acceptance fallback for the live GUI/API flow.
- The live Compose entry point is intentionally not a local first-run template. It requires only `PURESOC_CONNECTOR_MICROSOFT365_CLIENT_ID`, `PURESOC_CONNECTOR_MICROSOFT365_CLIENT_SECRET`, and `PURESOC_PROVIDER_TOKEN_KEY`; internal Postgres, MinIO, Redis, scanner, renderer, API trusted origin, callback URL derivation, and production hardening values are fixed in `code/compose.yml`.
- The Compose `puresoc-migrator` service runs `pnpm prisma:migrate:deploy` before API startup, live Compose also wraps `puresoc-api` with that command, and the API process itself runs `npm run prisma:migrate:deploy` in Prisma mode before listening unless `PURESOC_API_RUN_MIGRATIONS_ON_STARTUP=false`. These fallbacks cover platforms that skip one-shot services, ignore `depends_on`, or start the Dockerfile CMD directly. They must stay idempotent and must not use `prisma migrate reset`, `db push --force-reset`, `docker compose down -v`, or volume deletion.
- OIDC/social-login transient authorization state now uses the runtime-selected state store. Prisma mode persists state and nonce only as hashes, stores the PKCE verifier inside an auth-owned encrypted envelope, and requires `PURESOC_AUTH_OIDC_TRANSIENT_STATE_KEY` outside local development.
- Live PostgreSQL migration/runtime smoke is `pnpm prisma:smoke:postgres` from `code/`; it must target a disposable database URL and covers checked-in migrations plus representative Prisma repository CRUD without third-party providers or provider writes.
- Live Redis job-runtime smoke is `pnpm jobs:smoke:redis` from `code/`; it must target a local/disposable Redis URL and covers the `@puresoc/jobs` Redis-backed queue adapter without enabling provider writes or live external integrations.
- Redis-backed job claiming uses per-job claim locks and explicit stale-running recovery/terminal cleanup hooks; recovery thresholds and cleanup cadence are operator-owned and must be tuned so long-running jobs are not retried while still legitimately running.
- Provider-token custody smoke is `pnpm provider-token:smoke` from `code/`; it is local/disposable only, covers Microsoft 365 `local-env-key-ring` plus deterministic `fake-secret-manager-test` metadata, and must not print provider tokens, OAuth codes, client secrets, key material, or decrypted credential payloads.
- `fake-secret-manager-test` is a Microsoft 365 provider-token custody contract fixture only. It models key-version metadata, active/previous lookup, missing-key failure, and rotation/backfill runbook summaries without live secret-manager/KMS calls; production startup must reject it.
- Provider-token custody readiness uses `PURESOC_PROVIDER_TOKEN_CUSTODY_TARGET_KIND=local|in_a_box|saas`. `local-env-key-ring` is the only real implemented custody provider; `saas` readiness must report `provider_token_saas_external_custody_deferred` until a real KMS/HSM/secret-manager adapter and approved deployed smoke exist.
- The live Compose template is secret-minimal: API/scheduler/migrator use Prisma/Postgres through a generated internal URL, API uses bundled MinIO/S3 and the local HTTP upload-scanner, Microsoft 365 connector runs in live read-only mode, social login and Stripe stay disabled, and provider-token rotation/custody extras must stay out of the live `.env.example`.
- Compose upload scanning uses `puresoc-upload-scanner` as the app-facing HTTP adapter and `puresoc-clamav` as the private ClamAV/FreshClam engine. Keep `clamd` TCP internal-only, persist `/var/lib/clamav` in a volume, and do not expose port 3310 through public ingress.
- Microsoft 365 customer Graph connection uses `PURESOC_CONNECTOR_MICROSOFT365_CLIENT_ID`, `PURESOC_CONNECTOR_MICROSOFT365_CLIENT_SECRET`, and `PURESOC_PROVIDER_TOKEN_KEY` in the live compose. Register one PureSOC-controlled multitenant Entra app in the operator tenant for this connector; customer tenants connect through admin consent and store tenant IDs/tokens per `ProviderConnection`. Microsoft Entra user sign-in uses `PURESOC_AUTH_MICROSOFT_ENTRA_*`, is disabled by default, and is only for PureSOC users logging into the app with Microsoft.
- Production Prisma-mode `PURESOC_AUTH_OIDC_TRANSIENT_STATE_KEY` is required whenever at least one Microsoft/Google/GitHub social-login provider is enabled. Do not put actual social-login secrets in the default installer template.
- When `PURESOC_PROVIDER_TOKEN_PREVIOUS_KEYS` is configured, readiness must require explicit operator confirmations for the previous-key window, ciphertext backfill plan, and key-retirement plan through `PURESOC_PROVIDER_TOKEN_PREVIOUS_KEY_WINDOW_CONFIRMED`, `PURESOC_PROVIDER_TOKEN_BACKFILL_PLAN_CONFIRMED`, and `PURESOC_PROVIDER_TOKEN_KEY_RETIREMENT_PLAN_CONFIRMED`. These flags are metadata only and do not execute backfill or retire keys.

- API request context must ignore `X-Forwarded-For` and `Forwarded` headers by default. Forwarded client IPs may affect audit context or rate-limit keys only when `PURESOC_API_TRUST_FORWARDED_HEADERS=true` and `PURESOC_API_TRUSTED_PROXY_IPS` explicitly lists the socket peer proxy address.
